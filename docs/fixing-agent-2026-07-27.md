## Роль

Ты — инженер, закрывающий дефекты инвестиционной платформы. Задача разбита на пять блоков.
Блок 0 — предусловие: без него нельзя катить ветку на staging. Блоки 1–2 обязательны,
3–4 решаются по ходу.

Работай блоками, а не отдельными пунктами: в блоке 1 у обоих дефектов общий корень, и
правка одного места оставит второй.

**Каждую правку на бэкенде сопровождай тестом, который падает до неё и проходит после.**
Правки на клиенте проверяй в браузере (`npm --prefix mobile run web`) и прикладывай, что

## ~~Блок 0. Staging не поднимается — предусловие~~ — ЗАКРЫТ 27.07.2026

Обе миграции применены к Neon (сирот в `daily_checkins` не оказалось — 0 из 2 строк).
`render.yaml` переведён на `NODE_ENV=production`, миграции гоняются из `startCommand`,
потому что `preDeployCommand` у Render только на платных планах, а сервис на free.
Проверено: `GET /api` → `Hello World!`, `/api/quests` и `/api/activity/streak` под
инвестором → 200, старт с `synchronize` не вносит ни одного схемного изменения.

`npm run start:dev` с `backend/.env.local` (Neon) не стартовал вообще:

```
ERROR [TypeOrmModule] Unable to connect to the database. Retrying (1)...
QueryFailedError: column "user_id" of relation "daily_checkins" contains null values
```

и так по кругу.

**Причина.** В базе `daily_checkins.user_id` — `character varying` без FK, а сущность
`backend/src/activity/entities/daily-checkin.entity.ts` объявляет `uuid` + `@ManyToOne`.
`synchronize` (включён для всего, что не `production`) привести varchar к uuid на непустой
таблице не умеет и пытается добавить колонку заново — отсюда «contains null values».
Миграции, которые ровно это чинят, к базе не применялись: таблицы `migrations` там нет.

**Что сделать.**

1. Прогнать `npm --prefix backend run migration:run` против Neon. Обе миграции
   (`1785110400000-ReferralSystem`, `1785283200000-DailyCheckinUserFk`) идемпотентны,
   вторая перед добавлением FK удаляет строки без пользователя.
2. Решить вопрос по существу: сейчас staging живёт на `synchronize`, а миграции в
   `render.yaml` не вызываются вовсе. Либо добавить `preDeployCommand` с
   `migration:run:prod` и перевести staging на `NODE_ENV=production`, либо явно
   зафиксировать в `render.yaml` комментарием, что миграции гоняются руками — но тогда
   любой новый несовместимый `ALTER` будет валить деплой так же.
3. После этого проверить, что `GET /api` отвечает `Hello World!`, а `/api/quests` и
   `/api/activity/streak` под инвестором отдают 200.

## ~~Блок 1. Отложенные изменения ломают денежную модель — критический~~ — ЗАКРЫТ 27.07.2026

Развилка решена в пользу строгого варианта. `assertChangesApplicable` в
`projects.service.ts` вызывается из `update`, `approve` и `adminUpdate`. Два уровня:
арифметические инварианты (`totalTickets < ticketsSold`, `targetAmount < collectedAmount`)
не может нарушить никто, включая модератора; запрет на правку цены и доли при
`ticketsSold > 0` действует для основателя и для применения его отложенной правки, а
`adminUpdate` сохраняет ручную переоценку — она и была задумана как отдушина.

Попутно нашлась дыра, которой в отчёте не было: `ticketPrice` выводится в `normalizeEdit`
при одном лишь *присутствии* ценового поля в DTO, поэтому при разъехавшейся хранимой цене
переоценка приходила отдельной строкой мимо проверки входов. `ticketPrice` добавлен
в `STAKE_FIELDS`.

Тесты: `backend/src/projects/edit-guard.spec.ts` — 9 из 15 падают на коде до правки.
Карточка модератора показывает продано/собрано над диффом, когда правка задевает цену.

Один корень: `update` и `approve` в `backend/src/projects/projects.service.ts` не сверяли
предлагаемые значения с тем, что уже продано.

### 1.1. Число тикетов можно опустить ниже проданного

`update` (`projects.service.ts:317`) защищает ровно одно поле:

```ts
if (dto.equityOfferedPercent !== undefined && project.ticketsSold > 0 && …) {
  throw new BadRequestException('Cannot change the offered equity share after tickets have been sold.');
}
```

`totalTickets`, `targetAmount`, `priceTierCount`, `priceTierIncrementPercent` такой проверки
не имеют, хотя все четыре перечислены в `PRICE_INPUT_FIELDS` и пересчитывают цену раунда.

Воспроизведение (2 шага, оба через UI или API):

```
1. founder: PATCH /api/projects/:id { "totalTickets": 50 }
   на проекте, где ticketsSold = 100, collectedAmount = 5 000 000, status = funded
   → 200, changes уходят в pendingChanges
2. admin:  POST /api/projects/:id/approve
   → 200, применено
```

Состояние после: `total_tickets=50, tickets_sold=100, ticket_price=75 382.95,
collected_amount=5 000 000.00`.

Что видит инвестор на карточке проекта:

- «Осталось тикетов **−50 / 50**» — отрицательный остаток;
- «Один тикет» вырос с **0,4 % → 0,8 %** компании: держатели 100 тикетов получили 80 %
  вместо проданных им 40 %;
- цена тикета пересчиталась в 130 261,71 ֏ по новой лестнице.

Дальше по этим числам будут считаться дивиденды (`project-finance.service.ts` делит по
строкам тикетов) и возврат (`project-funding.service.ts`) — то есть испорченная доля
разъедется в реальные выплаты.

### 1.2. `approve` применяет изменения вслепую

`approve` (`projects.service.ts:579`):

```ts
if (project.pendingChanges) {
  Object.assign(project, project.pendingChanges);
}
```

Между отправкой правки и решением модератора проходит время, за которое проект успевает
продать ещё тикеты. Даже корректная на момент отправки правка (`totalTickets` с 100 до 90
при 80 проданных) к моменту одобрения может стать невалидной. Проверка нужна **в момент
применения**, а не только в момент отправки.

Тот же `Object.assign` без проверок стоит и в `adminUpdate` (`projects.service.ts:378`) —
модератор правит живой проект напрямую, минуя очередь.

### Что сделать по блоку

Заведи одну функцию проверки правки — «допустимо ли применить этот набор полей к этому
проекту прямо сейчас» — и вызывай её из трёх мест: `update`, `approve`, `adminUpdate`.
Минимум, что она обязана запрещать при `ticketsSold > 0`:

- `totalTickets < ticketsSold` — безусловный отказ;
- `targetAmount` ниже уже собранного `collectedAmount`;
- изменение `priceTierCount` / `priceTierIncrementPercent` / `targetAmount` / `totalTickets`,
  если это делает цену уже проданных тикетов несогласованной с `collectedAmount` —
  здесь развилка, см. ниже.

Развилка, которую надо согласовать до правки: **можно ли вообще менять параметры
ценообразования после начала продаж.** Строгий вариант — запретить все четыре поля при
`ticketsSold > 0`, как уже сделано для `equityOfferedPercent`, и оставить основателю
текст, обложку, категорию, дедлайн. Мягкий — разрешать только рост (`totalTickets` и
`targetAmount` вверх), потому что он не отбирает у существующих держателей долю, а
размывает её предсказуемо. Я бы взял строгий: доля тикета — часть того, за что инвестор
заплатил, и ровно этим уже обоснован запрет на `equityOfferedPercent` в комментарии на
`projects.service.ts:330`.

Отдельно: карточка модератора показывает «Количество тикетов 100 → 50» как обычное
изменение. Даже после запрета на бэкенде выведи в
`mobile/src/screens/admin/ModerationDetailScreen.tsx` рядом с изменением фактическое
`ticketsSold` — модератор должен видеть, что продано, прежде чем одобрять правку цены.

### ~~2.2. Собранный проект уезжает в очередь модерации~~ — ЗАКРЫТ 27.07.2026

Развилка решена в пользу «не менять статус». Отдельный флаг не понадобился:
`pendingChanges != null` — это и есть «у живого проекта правка на рассмотрении», а
`status = PENDING_REVIEW` остался только за проектами, которые ещё ни разу не были живыми
(для них ревью — это шлюз, а не пауза). `statusBeforeReview` удалён вместе с колонкой.

Правки: `findPendingReview` берёт оба случая; `update`/`approve`/`reject`/`cancelReview`
меняют статус только у проекта из PENDING_REVIEW; «одна правка за раз» читается с
`pendingChanges`. Клиент: карточка основателя и чип «на рассмотрении» в разделе «Все»
тоже смотрят на `pendingChanges`.

Миграция `1785369600000-DropStatusBeforeReview` сначала возвращает статус проектам,
висящим на ревью в момент деплоя, и только потом дропает колонку — иначе собранный
проект молча стал бы активным. **Руками её не катить:** развёрнутый API ещё читает
`status_before_review`, дроп уронил бы живой сервис. Она отработает из `startCommand`
непосредственно перед стартом нового кода.

Тесты: `backend/src/projects/review-status.spec.ts`.

### 2.2 (исходное описание). Собранный проект уезжает в очередь модерации

`update` (`projects.service.ts:365-369`) ставит `status = PENDING_REVIEW` любому проекту,
включая `FUNDED`. Прежний статус сохраняется в `statusBeforeReview` и восстанавливается в
`approve`/`reject`, так что тупика нет — но проект, в который уже вложено 5 000 000 ֏,
на время ревью косметической правки числится «на модерации» и лежит в очереди рядом с
непроверенными черновиками.

Это ровно тот пункт, что в `docs/fixing-agent.md` (4.2) был оставлен как есть для
активных проектов. Для `funded` он выглядит хуже: сбор уже закончен, останавливать нечего,
а статус всё равно откатывается на две ступени назад.

Предлагаемое решение (то же, что предлагалось в 4.2, теперь с более веским поводом):
не менять `status` на время ревью правки, а держать факт «есть изменения на рассмотрении»
в `pendingChanges` + отдельном флаге, и по нему показывать бейдж и попадание в очередь.
Тогда `statusBeforeReview` становится не нужен. Если решишь оставить как есть — запиши
обоснование в комментарии рядом с `update`, чтобы третий прогон не заводил дефект снова.

## Порядок работы

1. Блок 0 — иначе нечего проверять на staging.
2. Блок 1 целиком, одним заходом; развилку по ценообразованию согласуй до правки.

## Как проверять

Тесты бэкенда, которые обязаны падать на текущем коде:

- `PATCH /api/projects/:id { totalTickets: N }` при `ticketsSold > N` → 400, `pendingChanges` пуст;
- правка отправлена при `ticketsSold=80, totalTickets=90`, затем продано ещё 15 тикетов,
  затем `approve` → 400 либо изменение отклонено, `total_tickets` не опускается ниже
  `tickets_sold`;
- `adminUpdate` с тем же телом → 400;
- `GET /partners/admin/applications` под инвестором → 403, под админом → 200 и заявка в списке;
- после `review` заявки её статус у заявителя меняется с `pending`.

Инварианты после каждого блока — сквозная сверка из `docs/testing-agent.md`: для каждого
проекта `ticketsSold` равен сумме количеств в таблице тикетов и не превышает `totalTickets`;
сумма всех балансов кошельков плюс эскроу всех проектов плюс их доступные остатки меняется
ровно на величину внешних пополнений и выводов. Расхождение на копейку — тоже расхождение.

Клиентские правки проверяй в браузере на локальном стенде и прикладывай, что увидел:
собранный проект без блока покупки, отключённая кнопка модерации с подписью, ввод
количества выше остатка, экран заданий при выключенном бэкенде.

## Что трогать не надо

Прогон 27.07 подтвердил, что эти места считают верно, — не задень их правками блока 1:

- порядок списания при покупке: сначала `investCredit`, остаток из `balance`;
- покупка через границу раунда — по цене каждого тикета, а не по средней;
- полная распродажа при 100 тикетах на 4 раунда даёт `collectedAmount = targetAmount`
  ровно, последний тир добирает накопленное округление;
- переход в `funded` при `ticketsSold = totalTickets` и уход проекта из вкладки «Собираются»;
- реферальные начисления: `level_bonus` 100 ֏ и `deposit_percent` 1 % от первого пополнения,
  оба `pending` со сроком +14 дней, обе строки видны в «Истории начислений»;
- награды за задания уходят в `investCredit`, а не в `balance`, и повторно не выдаются.
