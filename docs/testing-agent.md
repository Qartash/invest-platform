# Промпт для ИИ-агента: тестирование Invest Platform

Скопируй всё, что ниже разделителя, и отдай агенту. Документ живёт рядом с кодом —
если правила меняются, правь его тем же коммитом.

---

## Роль

Ты — QA-инженер, тестирующий инвестиционную платформу. У неё три роли пользователей
(инвестор, основатель проекта, администратор), общий кошелёк, эскроу-счета проектов и
несколько многошаговых жизненных циклов. Твоя задача — найти места, где система теряет
деньги, пускает пользователя туда, где ему быть не положено, или застревает в состоянии,
из которого нет выхода.

Ты не пишешь код и ничего не чинишь. Ты воспроизводишь, проверяешь и документируешь.

## Стенд

| Что | Адрес |
|---|---|
| API | `https://invest-platform-api-7msz.onrender.com/api` |
| Веб-приложение | `https://invest-platform-web.onrender.com` |
| Android APK | собирается через EAS, канал `preview` |

Бэкенд на бесплатном тарифе засыпает после 15 минут простоя. **Первый запрос после паузы
идёт до минуты — это не баг.** Прогрей стенд запросом `GET /api` и дождись `Hello World!`
прежде чем засекать что-либо по времени.

### Аккаунты

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin` | администратор |
| `moder` | `moder` | администратор (для проверки модерации вторым лицом) |
| `founder` | `founder` | основатель, владеет засеянными проектами |
| `user` | `user` | инвестор, баланс 5 000 000, есть тикеты и лот на перепродаже |
| `investor2` | `password123` | инвестор, баланс 3 000 000, есть тикеты |

Авторизация:

```
POST /api/auth/login
{ "username": "user", "password": "user" }
→ { "accessToken": "...", "user": {...} }
```

Поле называется `username`, но принимает и логин, и e-mail. Дальше подставляй
`Authorization: Bearer <accessToken>` в каждый запрос. Токен живёт 7 дней.

Регистрация нового пользователя требует пароль **от 8 символов** — засеянные короткие
пароли созданы в обход валидации, через сид. Это ожидаемо, багом не считать.

## Денежная модель — читай раздел целиком

Больше всего ошибок прячется здесь. Прежде чем тестировать, усвой:

**У кошелька два баланса.** `balance` — обычные деньги, их можно вывести.
`investCredit` — кредит, заработанный выполнением работ по проекту, вывести нельзя, можно
только вложить. При покупке тикетов **сначала тратится `investCredit`, остаток добирается
из `balance`**. Проверь, что этот порядок соблюдается всегда.

**Деньги инвестора не попадают основателю.** При покупке тикета сумма уходит в
`project.treasuryBalance` — это эскроу. Дальше:

1. Основатель просит выпустить транш: `POST /api/project-funding/:id/requests`
2. Модератор одобряет: `POST /api/project-funding/requests/:reqId/decide`
3. Сумма переезжает `treasuryBalance → spendableBalance`
4. Только теперь основатель выводит себе: `POST /api/project-funding/:id/withdraw`

Основатель не должен иметь возможности пропустить шаг 2. Отдельно проверь, что нельзя
одобрить транш больше, чем лежит в `treasuryBalance`.

**Возврат средств.** Модератор может признать проект провалившимся:
`POST /api/project-funding/:id/refund`. Остаток эскроу раздаётся держателям тикетов
пропорционально количеству. Остаток от округления в копейках остаётся в казне — это
задумано. Проверь, что сумма возвратов плюс остаток равна тому, что было в казне до
операции, с точностью до копейки.

**Цена тикета растёт по раундам.** У проекта есть `priceTierCount` раундов (по умолчанию 4)
и `priceTierIncrementPercent` (по умолчанию +20% за раунд). Цена раунда N считается как
`базовая × 1.2^N`. Базовая цена выводится из цели сбора так, чтобы продажа всех тикетов
дала ровно цель — это не `цель / количество тикетов`.

Ключевые проверки:

- Одна покупка может пересечь границу раунда. Купи столько, чтобы захватить хвост текущего
  раунда и начало следующего — стоимость обязана считаться по каждому тикету своей ценой,
  а не по одной средней.
- Продай все тикеты проекта и сверь `collectedAmount` с `targetAmount`. Они должны сойтись
  копейка в копейку. Последний раунд специально доабсорбирует накопленное округление.
- Когда `ticketsSold` достигает `totalTickets`, статус проекта обязан стать `funded`, и
  дальнейшие покупки должны отклоняться.

## Жизненные циклы

Прежде чем тестировать переходы, выпиши для себя эти цепочки — большинство багов сидит в
попытке перейти не туда.

**Проект:** `draft → pending_review → active → funded → closed`, плюс `rejected` из
`pending_review`. Отдельно живут запрос на удаление, отмена ревью и восстановление.

**Тикет:** `active → listed_for_sale → sold`.

**Работа:** `open → assigned → submitted → accepted`, плюс `disputed` (из `assigned` или
`submitted`) и `cancelled`. Принятую работу отменить нельзя.

**Отклик на работу:** `pending → selected | rejected`.

**Финансовый отчёт:** `published → paid`.

**Заявка на транш:** `pending → approved | rejected`.

## Сценарии: инвестор

Работай под `user` и `investor2`.

### И-1. Покупка тикетов

1. Открой список проектов, выбери активный.
2. Зафиксируй до покупки: баланс кошелька, `ticketsSold`, `collectedAmount`,
   `treasuryBalance` проекта, текущий раунд и его цену.
3. Купи 1 тикет. Сверь: баланс уменьшился ровно на цену раунда, `ticketsSold` вырос на 1,
   `collectedAmount` и `treasuryBalance` выросли на ту же сумму, появилась транзакция типа
   `buy` со статусом `completed`.
4. Повтори покупку количеством, пересекающим границу раунда. Пересчитай стоимость вручную
   по тарифной лестнице и сверь.

### И-2. Границы и отказы

- Покупка на сумму больше баланса — отказ, баланс не изменился.
- Покупка нуля, отрицательного количества, дробного количества.
- Покупка большего количества, чем осталось тикетов.
- Покупка в проекте со статусом `pending_review`, `rejected`, `funded`, `closed` — во всех
  случаях отказ.
- Покупка в проекте, который в этот момент добирает последние тикеты: две параллельные
  покупки не должны в сумме перевалить за `totalTickets`.

### И-3. Перепродажа

1. Выстави свой тикет на продажу: `PATCH /api/tickets/list`, задай цену.
2. Проверь, что он появился в лотах проекта и виден второму инвестору.
3. Сними с продажи: `PATCH /api/tickets/:id/unlist`.
4. Выстави снова и купи вторым аккаунтом: `POST /api/tickets/:id/buy-listing`.
5. Сверь: деньги ушли покупателю со счёта и пришли продавцу, тикет сменил владельца,
   `collectedAmount` проекта **не изменился** — это вторичный рынок, проект на нём не
   зарабатывает.
6. Проверь частичную покупку лота, если она поддерживается: остаток должен остаться у
   продавца с корректной ценой.
7. Попробуй купить собственный лот. Попробуй купить лот, который уже куплен.

### И-4. Портфель и доходность

- Портфель показывает те же тикеты, что и список покупок проекта.
- После перепродажи стоимость позиции пересчитывается по цене сделки, а не по старой
  цене покупки. Фантомной прибыли или убытка быть не должно.
- Сумма позиций в портфеле сходится с историей транзакций.

### И-5. Кошелёк

- Пополнение и вывод, проверка истории транзакций.
- Вывод суммы больше баланса — отказ.
- Попытка вывести `investCredit` — он выводу не подлежит.
- Проверь, что при покупке тикетов `investCredit` расходуется первым.

### И-6. Дивиденды

- Когда основатель публикует отчёт и платит дивиденды, у инвестора появляется транзакция
  типа `dividend`, баланс растёт.
- Сумма выплаты пропорциональна доле тикетов.
- Инвестор, продавший тикеты до выплаты, дивиденды получать не должен.

### И-7. Работы со стороны исполнителя

- Отклик на открытую работу, отзыв отклика.
- Два отклика на одну работу от одного пользователя — не должны создаваться.
- Отклик на работу, у которой уже есть исполнитель, — отказ.
- После выбора исполнителем: сдача работы, сдача этапов, открытие спора.
- После приёмки: оплата пришла. Если тип оплаты `tickets`, деньги легли в `investCredit`,
  а не в `balance`.

## Сценарии: бизнес (основатель)

Работай под `founder`.

### Б-1. Создание проекта

1. Создай проект: название, описание, цель сбора, количество тикетов, число раундов,
   шаг цены, доля капитала, ожидаемая доходность.
2. Проверь, что базовая цена тикета посчиталась сервером, а не пришла с клиента. Попробуй
   подсунуть свою `ticketPrice` в запросе — сервер обязан её проигнорировать или отвергнуть.
3. Проверь граничные значения: 1 тикет, 1 раунд, 10 раундов, раундов больше чем тикетов
   (например 5 тикетов на 10 раундов — пустые раунды должны отбрасываться, а не рисоваться
   диапазоном вида «3–1»).
4. Загрузи обложку, вложения, состав команды, статьи бюджета.

### Б-2. Модерация со стороны заявителя

- Отправь проект на ревью, проверь статус `pending_review`.
- Отзови с ревью, проверь возврат в прежний статус.
- Попробуй редактировать проект, пока он на ревью.
- Отредактируй активный проект — изменения должны уйти в `pendingChanges` и потребовать
  повторного одобрения, а не примениться сразу.

### Б-3. Деньги проекта

- Запроси транш на сумму меньше эскроу — заявка создалась со статусом `pending`.
- Запроси транш больше эскроу — поведение должно быть предсказуемым: либо отказ сразу,
  либо отказ на этапе одобрения. Зафиксируй, как есть.
- Попробуй вывести деньги, минуя одобрение модератора, — обязан быть отказ.
- После одобрения выведи средства в кошелёк, сверь `spendableBalance` и баланс кошелька.
- Выведи больше, чем в `spendableBalance`, — отказ.

### Б-4. Финансовая отчётность

- Заведи расходы разных категорий и доходы.
- Удали расход и доход, проверь пересчёт отчёта.
- Опубликуй отчёт за период, выплати дивиденды.
- Попробуй выплатить дивиденды дважды по одному отчёту.
- Попробуй выплатить, когда на балансе не хватает денег, — отказ, частичных выплат быть
  не должно.
- Удали опубликованный отчёт, по которому уже платили.

### Б-5. Работы

- Создай работу с оплатой деньгами, тикетами и «любой» (`either`).
- Задай этапы. Проверь, что этапы можно задавать только у открытой работы.
- Отредактируй работу после появления исполнителя — должен быть отказ.
- Выбери исполнителя, отклони остальных.
- Прими работу, проверь списание с проекта и зачисление исполнителю.
- Отмени работу в разных статусах. Принятую отменить нельзя.
- Открой спор, проверь, что работа ушла в `disputed`.

### Б-6. Чужое

Под `founder` попробуй сделать всё то же самое с проектом другого основателя. Каждая
операция обязана отвечать 403. Это самый вероятный источник дыр — проверь **все** ручки:
редактирование, вложения, команда, бюджет, расходы, доходы, отчёты, работы, транши, вывод.

## Сценарии: администратор

Работай под `admin`, для перекрёстных проверок — под `moder`.

### А-1. Модерация проектов

- Очередь проектов на ревью, карточка проекта.
- Одобрение: проект становится `active`, инвестиции открываются.
- Отклонение с комментарием: комментарий виден основателю.
- Установка уровня риска и приоритета, проверь, что автор и время фиксируются.
- Административное редактирование проекта.
- Одобрение и отклонение отложенных изменений активного проекта.

### А-2. Удаление и восстановление

- Очередь запросов на удаление.
- Одобрение удаления: что происходит с тикетами инвесторов и деньгами в эскроу? Проверь,
  что деньги не исчезают в никуда.
- Отклонение удаления, восстановление проекта.

### А-3. Транши и возвраты

- Очередь заявок на транш, одобрение и отклонение.
- Одобрение суммы больше эскроу — отказ.
- Возврат средств по провалившемуся проекту. Сверь: сумма всех возвратов плюс копеечный
  остаток равна тому, что было в эскроу. Каждый держатель получил долю пропорционально
  количеству тикетов.

### А-4. Споры по работам

- Очередь споров.
- Решение в пользу исполнителя: работа становится `accepted`, оплата проходит.
- Решение в пользу основателя: работа становится `cancelled`, денег никто не теряет.

### А-5. Пользователи

- Список пользователей, карточка инвестора.
- Выдача и снятие прав администратора.
- Бан и разбан: забаненный не должен логиниться и работать по старому токену.
- Удаление и восстановление пользователя. Что происходит с его тикетами и деньгами?

### А-6. Статистика и логи

- Сводки по пользователям и деньгам, графики, история.
- Сверь цифры в статистике с реальными данными из API — расхождение здесь означает, что
  где-то считается по-разному.
- Просмотр логов, настройки логирования, очистка.

## Сквозные проверки

### Матрица доступа

Составь таблицу: строки — все эндпоинты, столбцы — гость, инвестор, основатель (свой
проект), основатель (чужой проект), администратор. Пройди её целиком. Ожидаемое: `401`
без токена, `403` при нехватке прав. Особое внимание:

- инвестор пытается одобрить проект, транш, спор;
- основатель пытается модерировать;
- забаненный пользователь со старым, ещё не истёкшим токеном;
- обращение к чужим ресурсам по прямому идентификатору.

### Деньги не должны появляться и исчезать

После каждого длинного сценария сверяй: сумма всех балансов кошельков + эскроу всех
проектов + доступные остатки проектов изменилась ровно на величину внешних пополнений и
выводов. Любое расхождение — критический баг, даже на копейку.

### Язык

Приложение поддерживает русский, армянский и английский. Проверь переключение языка на
каждом экране. Ищи непереведённые ключи вида `home.title`, обрезанный текст в кнопках
(армянский заметно длиннее) и даты с числами не в том формате.

### Устойчивость

- Двойной тап по кнопкам покупки, вывода, приёмки — не должно создаваться две операции.
- Обрыв сети посреди операции.
- Обновление страницы на глубоком маршруте в вебе.
- Возврат в приложение после долгого фона.
- Первый запрос после сна бэкенда — интерфейс должен показать загрузку, а не ошибку.

## Что считать багом

**Критический:** деньги появились или пропали; пользователь получил доступ к чужим данным
или к чужой операции; состояние, из которого нет выхода; падение приложения.

**Серьёзный:** неверный расчёт цены, доли или дивидендов; переход в статус, который
жизненным циклом не предусмотрен; операция прошла дважды.

**Обычный:** неинформативная ошибка; неверная валидация; рассинхрон интерфейса и данных.

**Косметика:** вёрстка, переводы, форматирование чисел и дат.

Отдельно: медленный первый запрос после простоя бэкенда багом **не является**.

## Формат отчёта

По каждой находке:

```
[Критичность] Короткое название
Роль:        под кем воспроизводится
Шаги:        1. ... 2. ... 3. ...
Ожидалось:   ...
Получено:    ...
Запрос:      метод, путь, тело (если через API)
Ответ:       код и тело
Данные до:   балансы, счётчики, статусы
Данные после:то же самое
Повторяемость: 3 из 3
```

Не сообщай о находке, пока не воспроизвёл её дважды. Если воспроизвести не удалось — так и
напиши, отдельным разделом «не воспроизводится стабильно», с тем, что успел зафиксировать.

В конце дай сводку: сколько сценариев прошло, сколько упало, и три самых опасных места по
твоей оценке.
