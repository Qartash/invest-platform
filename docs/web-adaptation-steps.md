# Промпты по шагам: адаптация под веб

Каждый шаг — отдельный промпт, копируется целиком в новую сессию.
Шаги идут строго по порядку: следующий опирается на предыдущий.

---

## ОБЩИЙ БЛОК

Этот текст добавляется в начало **каждого** шага. Без него агент рано или поздно
сломает мобилку.

```
Проект: mobile/ — один Expo-кодбейс (expo ~57, react-native 0.86, react 19.2),
собирается и в нативное приложение, и в веб через react-native-web
(app.json → web.bundler: metro, output: single). Бэкенд NestJS в backend/,
API общий для всех клиентов.

Задача этой сессии — только то, что описано ниже. Ничего сверх этого не делать.

НЕРУШИМЫЕ ПРАВИЛА:

1. Три клиента, а не два: нативное приложение, мобильный браузер, десктопный
   браузер. Мобильный браузер — это Platform.OS === 'web' при узком экране.
   Он должен выглядеть и вести себя как нативное приложение, а НЕ как десктоп.

2. Platform.OS === 'web' НИКОГДА не решает раскладку. Только ширина окна через
   useWindowDimensions(). Dimensions.get() для раскладки не использовать — он
   не пересчитывается при ресайзе окна браузера.
   Platform.OS остаётся только для возможностей платформы: linking в
   RootNavigator.tsx, WebView, image picker, src/utils/alert.ts, hover,
   клавиатура.

3. Существующее поведение ниже брейкпоинта md — неприкосновенно. Любое новое
   поведение добавляется как ветка ДЛЯ ШИРОКОГО экрана, а узкая ветка остаётся
   тем же кодом, что и была. Если приходится переписать общий код — старый
   визуальный результат на узком экране должен совпасть до пикселя.

4. Не трогать: src/api/, src/store/, backend/, имена роутов, структуру
   навигации, src/i18n/locales/*.json (кроме добавления новых ключей).

5. Отдельного API для веба не делать. Если данных не хватает — сказать об этом
   в отчёте, а не изобретать эндпоинт.

6. Не форкать компоненты на Foo.tsx + Foo.web.tsx ради пары стилей. Файловый
   сплит — только если реализации действительно расходятся.

ПРОВЕРКА ПЕРЕД ОТЧЁТОМ (обязательна, без неё не отчитываться):
- npx tsc --noEmit в mobile/ проходит;
- открыть веб-сборку и посмотреть на ширинах 375, 768, 1280, 1920.
  ВАЖНО: после смены ширины ОБЯЗАТЕЛЬНО перезагружать страницу. В панели
  браузера ресайз не порождает событий resize, react-native-web их не видит и
  отдаёт раскладку от прошлой ширины. Подробности и замеры — в
  docs/web-adaptation-baseline.md;
- на 375px сравнить со скриншотом ДО изменений — должно совпасть;
- проверить светлую и тёмную тему (src/theme/ThemeProvider.tsx);
- проверить языки en / hy / ru — армянский и русский длиннее английского и
  ломают узкие кнопки.

В отчёте написать: что сделано, что осталось, что решено не делать и почему.
Если что-то не проверено — сказать прямо, а не умолчать.
```

[ОБЩИЙ БЛОК]

Сделай фундамент для адаптивной раскладки. Пока без изменений внешнего вида —

   эквивалентным). Экспортируй из src/components/ui/index.ts.

4. Переведи захардкоженные maxWidth на токены:
   src/components/DatePickerModal.tsx:155 (360)
   src/components/ProjectFinancePanel.tsx:1404 (480)
   src/components/ProjectWorksPanel.tsx:947 (480)
   Значения не менять — только вынести в токены.

Ни один экран на этом шаге в PageContainer НЕ оборачивать. Это следующие шаги.

## ШАГ 2 — Навигация

```
[ОБЩИЙ БЛОК]

Сделай навигацию адаптивной.

Сейчас src/navigation/MainNavigator.tsx использует createBottomTabNavigator
с кастомным tabBar={(props) => <BottomDock {...props} />}
(src/components/BottomDock.tsx — плавающий док на 4 иконки без подписей,
выделение — заливная пилюля).

На широком экране нижний плавающий док — неправильный паттерн: на десктопе
навигация живёт слева. На узком экране (телефон и мобильный браузер) док должен
остаться ровно таким, как сейчас — включая useSafeAreaInsets, анимацию пилюли
и отсутствие подписей.

1. Боковой рейл для isWide: вертикальный, слева, с подписями (на десктопе место
   есть, а без подписей сайдбар читается хуже дока). Иконки берутся из тех же
   options.tabBarIcon, подпись из options.title — API BottomTabBarProps не менять.
2. Переключение по брейкпоинту. Решить, делать это внутри BottomDock или
   подменять tabBar — выбрать и объяснить выбор в отчёте.
3. Имена роутов и структуру Tab.Screen НЕ менять — иначе поломается
   src/navigation/linking.ts.
4. screenListeners с logEvent('navigation', ...) должен продолжать срабатывать
   в обоих режимах.
5. Проверить, что deep links из linking.ts живы: перезагрузка страницы на любом
   роуте, кнопка «назад» браузера, шаринг URL, documentTitle.
6. Сейчас headerShown: false. Реши, нужен ли на широком экране верхний бар
   (бренд / LanguageSwitcher / профиль). Если да — только для isWide, узкий
   экран остаётся без хедера.

Отдельно проверь мобильный браузер на 375px: док на месте, safe-area снизу
работает, ничего не уехало.
```

## ШАГ 3 — Экраны

Большой шаг. Разбить на подсессии по группам, иначе агент потеряет качество
к середине.

```
[ОБЩИЙ БЛОК]

Адаптируй под широкий экран экраны из группы <ГРУППА>. Остальные группы не трогать.

Группы (в этой сессии делаем одну):
  A) src/screens/auth/ — LoginScreen, RegisterScreen
  B) src/screens/investor/ — списки и ProjectDetailScreen
  C) src/screens/founder/ — CreateProjectScreen, MyProjectsScreen,
     ProjectFinanceScreen, ProjectWorksScreen
  D) src/screens/admin/ — ModerationScreen, ModerationDetailScreen,
     ModerationDisputesScreen, ModerationReleasesScreen, ModerationUserScreen,
     LogsScreen
  E) ProfileScreen, EditProfileScreen, ReportsScreen

Что делает широкий экран, по группам:
  A) центрированная карточка формы ограниченной ширины, а не растянутая на весь
     экран форма. GoogleSignInButton / OrDivider внутри той же карточки.
  B) сетка карточек в 2–3 колонки вместо одной колонки; для детали проекта
     рассмотреть мастер-деталь (список слева, детали справа) — если это требует
     новых данных от API, не выдумывать эндпоинт, а написать об этом в отчёте.
  C) формы в две колонки, длинные таблицы финансов и работ помещаются целиком
     без горизонтального скролла.
  D) здесь десктоп даёт больше всего: таблицы модерации и логов должны стать
     настоящими таблицами с колонками, а не списком карточек.
  E) две колонки: слева навигация по разделам профиля, справа содержимое.

Используй PageContainer и useBreakpoint из шага 1. Голых чисел в сравнениях
ширины быть не должно.

Узкая ветка каждого экрана остаётся текущим кодом без изменений. Если для
широкой ветки понадобилось переписать общий рендер — приложи к отчёту сравнение
узкого варианта до/после.
```

## ШАГ 4 — Модалки

```
[ОБЩИЙ БЛОК]

Адаптируй оверлеи. Все они сейчас сделаны под телефон — bottom-sheet или
полноэкранные. На десктопе это неправильно: нужен центрированный диалог
ограниченной ширины.

Список (src/components/): AvatarPickerModal, BuyListingModal, DatePickerModal,
HintModal, InvestorProfileModal, InvestorsListModal, ProjectHistoryModal,
RiskLevelModal, SellTicketModal, и src/components/ui/ActionSheet.

Для широкого экрана:
- центрированный диалог, maxWidth из токенов, скрим по всей площади;
- закрытие по Escape и по клику вне диалога (только Platform.OS === 'web');
- фокус уходит внутрь диалога при открытии и возвращается назад при закрытии;
- длинное содержимое скроллится внутри диалога, а не растит его за пределы окна.

Для узкого экрана — ровно текущее поведение, включая жесты и safe-area.

ActionSheet на десктопе, возможно, вообще не нужен как шит — может быть
уместнее поповер или выпадающее меню. Реши и объясни в отчёте.

Если у модалок есть общий каркас — вынеси его в один компонент, а не копируй
логику Escape/клик-вне в девять файлов.
```

## ШАГ 5 — Веб-специфика

```
[ОБЩИЙ БЛОК]

Здесь Platform.OS === 'web' уместен — это единственный шаг, где он решает
поведение. Но раскладку он по-прежнему не решает.

Важно: всё ниже относится и к мобильному браузеру тоже. Hover на тач-устройстве
может «залипать» после тапа — проверь, что не залипает.

1. Hover-состояния: PrimaryButton, Card, ListRow, DisclosureRow, ProjectCard,
   HoldingCard, OwnedProjectCard, TeamMemberCard, Pill, SegmentedTabs.
   Без них десктоп читается как сломанный сайт.
2. Видимый focus-ring для навигации с клавиатуры; логичный Tab-порядок в формах;
   submit по Enter в LoginScreen / RegisterScreen и в формах founder.
3. cursor: pointer на всём кликабельном.
4. Скролл колесом: проверь, что вложенные ScrollView (ProjectFinancePanel,
   ProjectWorksPanel, длинные модалки) не перехватывают колесо у страницы.
5. RichTextEditor.tsx и RichTextView.tsx — @10play/tentap-editor поверх WebView,
   на вебе используется @10play/react-native-web-webview. Поведение отличается
   от нативного: проверь ввод, вставку, тулбар и выделение отдельно в браузере.
6. Веб-метаданные: favicon (assets/favicon.png уже прописан), <title> — сейчас
   частично через documentTitle в linking.ts, проверь что он корректен на всех
   роутах; добавь description и og-теги.
7. Выделение текста мышью: сейчас RN-компоненты часто его блокируют. Там, где
   пользователь захочет скопировать (суммы, id, логи) — разрешить.

Ничего из этого не должно изменить нативную сборку. Если сомневаешься —
оберни в Platform.OS === 'web'.
```
